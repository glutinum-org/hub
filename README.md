# Glutinum hub

Fable bindings generated by [Glutinum](https://github.com/glutinum-org/cli), one NuGet package per npm package.

Each binding is a folder of `bindings/`, self-contained: open it in your editor to work on one binding only.

```text
bindings/Glutinum.DateFns/
├── binding.json            the package, its subpaths, the bindings it references, the kind of tests, the overload cap
├── package.json            pins the version of the npm package the binding is generated from
├── Glutinum.DateFns.fsproj written by `./build.sh generate` from binding.json
├── Glutinum.DateFns.fs     generated, do not edit
├── Glutinum.DateFns.Extensions.fs   optional, hand-written helpers compiled after the generated file
├── CHANGELOG.md            one version per binding, released by EasyBuild.ShipIt
├── README.md
└── tests/                  optional, Scriptorium tests run in Node or in Chromium
```

The DOM and Node bindings (`Glutinum.Web`, `Glutinum.Node`) live in the [cli repository](https://github.com/glutinum-org/cli) as references of the generator, the bindings here consume them from NuGet.

## Commands

| Command | Description |
| --- | --- |
| `./build.sh list` | The bindings, their package and version |
| `./build.sh new <package> [--input <subpath>] [--external <binding>] [--tests node\|browser]` | Scaffold a binding and generate it |
| `./build.sh add-tests <binding> [--browser]` | Scaffold the tests of a binding |
| `./build.sh generate [<binding>] [--changed] [--check]` | Regenerate the bindings |
| `./build.sh test [<binding>] [--changed] [--noCache]` | Build the bindings and run their tests |
| `./build.sh upgrade <binding> [<version>]` | Pin a newer version of the npm package and regenerate |
| `./build.sh release` | Pack and push the new versions to nuget.org |
| `./build.sh lint`, `./build.sh format` | Formatting of the build and the tests |

A binding is named after the module Glutinum derives from the package: `date-fns` gives `Glutinum.DateFns`, `@types/leaflet` gives `Glutinum.Leaflet`. `<binding>` accepts the full name, the module or the package name.

## Dependencies between bindings

Glutinum generates a package together with every typed package it depends on, as modules of the same file. When a dependency is exposed by several bindings, generate it as its own binding and reference it:

```sh
./build.sh new @types/geojson
./build.sh new @types/leaflet --external Glutinum.Geojson
```

`Glutinum.Leaflet` then references `Glutinum.Geojson.GeometryObject` instead of embedding a copy, and the two bindings share the types. `binding.json` lists the externals, `./build.sh generate` and `./build.sh test` order the bindings accordingly.

`"maxOverloads": 32` in `binding.json` passes `--max-overloads 32` to the CLI: the overloads a signature gets at most from its union parameters, 16 when absent.

## Releases

Commits follow [Conventional Commits](https://www.conventionalcommits.org/): `feat`, `fix`, `chore`... A commit touching a binding folder is a change of that binding, its tests are excluded. Once the tests pass on `main`, EasyBuild.ShipIt opens a pull request with the changelog and the version of each binding changed. Merging it pushes the packages to nuget.org.

The `regenerate` workflow regenerates every binding when the cli repository publishes a release, and on demand with a version, and opens a pull request with the result.

## Working with an unreleased Glutinum

Set `GLUTINUM_CLI` to the `cli.js` of a checkout built with `./build.sh cli`:

```sh
GLUTINUM_CLI=../cli/cli.js ./build.sh generate
```
